1. Resumen ejecutivo
DeUna será un sistema para registrar, identificar, custodiar y entregar paquetes en un punto de recepción. El flujo
principal empieza cuando un vendedor entrega un paquete; el operador registra la información, el sistema genera un
código de retiro y un código QR, y el vendedor puede comunicar estos datos a su comprador. Posteriormente, el
comprador se presenta en el punto DeUna, se valida el código/QR, se registra el pago correspondiente y el paquete
pasa a estado «Entregado».
    Principio de diseño
    El sistema debe minimizar el tiempo de atención en mostrador y reducir errores de identificación. El paquete debe
    poder localizarse por código, QR, nombre del comprador, celular del vendedor o estado.




2. Objetivos del sistema
      Centralizar el registro de todos los paquetes recibidos por DeUna.
      Asignar a cada paquete un identificador único, fácil de comunicar y fácil de visualizar físicamente.
      Generar automáticamente un código QR asociado al paquete para facilitar el retiro.
      Permitir que el operador consulte y filtre paquetes pendientes o entregados.
      Controlar el plazo de permanencia de 7 días y calcular una comisión adicional cuando corresponda.
      Registrar la entrega y el pago realizado por el comprador al momento del retiro.
      Mantener trazabilidad de quién recibió el paquete, cuándo se recibió y cuándo fue entregado.
      Facilitar reportes básicos de operación y conciliación de caja.

5. Flujo operativo principal
1. Recepción: El vendedor llega al punto DeUna con uno o varios paquetes.
2. Registro: El operador crea un registro por paquete e introduce los datos obligatorios.
3. Identificación: El sistema asigna un número correlativo a la lista y construye el código visible: inicial del nombre
del comprador + número. Ejemplo: «M-8».
4. QR: El sistema genera un QR único que codifica un identificador seguro del paquete y abre una ficha de
consulta/validación.
5. Entrega de información: El operador entrega o comparte el QR/código al vendedor para que este lo envíe al
comprador.
6. Custodia: El paquete queda con estado «Pendiente». El sistema calcula automáticamente los días transcurridos.
7. Retiro: El comprador se presenta, proporciona el QR o código y el operador verifica la coincidencia con el
registro.
8. Cobro: El sistema calcula el importe a pagar, incluyendo la comisión por atraso cuando corresponda.
9. Entrega: Una vez validado el pago y la persona autorizada, el operador marca el paquete como «Entregado» y
registra fecha/hora de entrega.
10. Trazabilidad: El sistema conserva el historial de la operación para consultas y reportes.

10. Flujo de entrega al comprador
1.   El comprador muestra el QR recibido o comunica el código, por ejemplo «M-8».
2.   El operador localiza el registro y verifica que el paquete esté en estado «Pendiente».
3.   El sistema muestra comprador, persona autorizada, fecha de recepción, días transcurridos y monto a pagar.
4.   El operador verifica que quien retira coincida con la persona registrada o registra una autorización excepcional
     según política de DeUna.
5.   El sistema calcula el total: tarifa base + comisión de atraso, si corresponde.
6.   El operador registra el pago y su medio de pago.
7.   El operador confirma la entrega. El estado cambia a «Entregado».
8.   El sistema registra fecha/hora, usuario operador y, opcionalmente, evidencia de entrega.

11.1. Experiencia de uso recomendada
      El registro de un paquete debe poder completarse en pocos pasos y con campos agrupados por persona y paquete.
      El botón «Registrar y generar QR» debe ser la acción principal del formulario.
      El código M-8 debe mostrarse en tamaño grande y alto contraste.
      La pantalla de entrega debe permitir resolver la operación desde un único lugar, sin navegar por varias pantallas.
      Los paquetes atrasados deben tener una señal visual claramente distinguible.
      Las acciones irreversibles como «Marcar Entregado» deben requerir confirmación.

13. Reglas de negocio
RN-01 — Cada paquete debe tener un ID interno único.
RN-02 — Un paquete nuevo inicia en estado «Pendiente».
RN-03 — Solo un paquete pendiente puede pasar normalmente a «Entregado».
RN-04 — La fecha/hora de recepción se genera automáticamente y no debe ser editable por un operador sin permiso
especial.
RN-05 — La numeración de lista debe seguir un criterio consistente y configurable (reinicio diario, mensual o
secuencia continua).
RN-06 — El código visible se genera automáticamente y no debe ser digitado manualmente por el operador.
RN-07 — El QR identifica al paquete, pero no debe exponer información personal innecesaria.

15. Casos especiales y validaciones
        Se intenta registrar un paquete sin nombre del comprador: impedir el guardado y mostrar mensaje claro.
        El comprador tiene un nombre compuesto o tildes: normalizar correctamente la inicial.
        Dos paquetes tienen el mismo comprador: ambos deben diferenciarse por número, código e ID/QR.
        Un tercero retira el paquete: debe existir un autorizado registrado o una excepción documentada según la política
         interna.
        El QR está dañado: el código M-N debe permitir búsqueda manual.
        El paquete ya fue entregado y se intenta entregarlo nuevamente: bloquear la operación normal.
        El operador introduce un código inexistente: mostrar «Paquete no encontrado» sin revelar información adicional.
        No existe conexión a internet: definir explícitamente si el sistema funcionará sin conexión. Para MVP se
         recomienda requerir conexión y mostrar un estado de conectividad.
        El monto cobrado difiere del calculado: pedir permiso especial y registrar el motivo en auditoría.
        El plazo de 7 días cambia en configuración: se debe definir desde qué momento afecta la nueva regla; se
         recomienda no modificar retrospectivamente retiros cerrados.

19. Decisiones que deben aprobarse antes de programar
Para evitar retrabajos, el equipo de desarrollo debería cerrar estas decisiones durante la etapa de análisis:
      ¿La numeración «8» se reinicia diariamente, mensualmente o nunca?
      ¿El código M-8 debe ser único en todo el sistema o solo dentro de la numeración activa?
      ¿Cuál será la tarifa base del servicio por paquete?
      ¿La comisión por superar 7 días será un monto fijo o un porcentaje?
      ¿Se cobrará por paquete, por día adicional o una sola vez al superar el plazo?
      ¿Qué documento o mecanismo se usará para validar que la persona que recoge está autorizada?
      ¿Se debe almacenar descripción, foto o ubicación física del paquete?
      ¿Se permitirá funcionamiento sin internet?
      ¿Cuál será el medio de pago preferido y qué comprobante se entregará?
      ¿Se enviará el QR automáticamente al comprador o el vendedor lo compartirá manualmente?
      ¿Qué política de retención y privacidad aplicará a los datos personales?



20. Definición de terminado (Definition of Done)
      Los requerimientos funcionales del MVP están implementados y probados.
      Existe una base de datos consistente y respaldable.
      Los roles y permisos fueron verificados.
      La generación de código y QR fue probada con nombres reales y duplicados.
      La regla de 7 días tiene pruebas para los límites exactos y casos atrasados.
      El flujo completo recepción → pendiente → pago → entrega funciona de extremo a extremo.
      Existe registro de auditoría para operaciones críticas.
      El sistema cuenta con manual mínimo de uso para operadores.
      QA valida los criterios de aceptación sin defectos críticos abiertos.
      La solución fue desplegada en un entorno de producción o piloto y se verificó la recuperación desde respaldo.

21. Conclusión
La solución propuesta para DeUna debe centrarse en un flujo operativo rápido y controlado: registrar el paquete una
sola vez, identificarlo mediante un código corto y un QR, custodiarlo bajo un estado «Pendiente», aplicar
automáticamente la regla de permanencia de 7 días, registrar el pago al momento del retiro y cerrar la operación como
«Entregado».
Este documento constituye una base de SRS para que un equipo de software pueda elaborar historias de usuario,
diagramas UML/BPMN, modelo entidad-relación, arquitectura, prototipos de interfaz, estimación de esfuerzo, plan de
pruebas y backlog del MVP.
